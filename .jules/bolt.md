## 2026-07-19 - Batch Processing and Split Optimization in ChromaDB Indexer
**Learning:** For vector indexers operating on a large corpus, indexing documents one by one causes extreme overhead (especially in virtualized database or API boundaries) due to separate network or filesystem commits per write. Consolidating writes into small chunks (e.g. `BATCH_SIZE = 20`) reduces database transaction frequency and dramatically improves performance. Additionally, evaluating text word-counts via `.split()` calls on massive strings parses the entire string redundantly; using a bounded split with a `maxsplit` parameter (`split(None, LIMIT + 1)`) optimizes CPU and memory usage significantly on large documents.
**Action:** Always implement batch ingestion with size boundaries (e.g., 20 to 100) and avoid full-string splits when checking limits. Use `split(None, limit)` to stop parsing once the target threshold is reached. Use state objects with clean nested flush mechanisms and robust clear triggers inside a `finally` block to prevent "batch poisoning" where a single faulty chunk corrupts subsequent indexing batches.
